# desire 1.0 路线图

目标:在 API 稳定承诺(语义化版本硬保证)发布之前,把公开面收敛到
"我们愿意用 1.x 维护五年的形状"。本文是 1.0 的工作清单,按"必须先决"
→ "有意冻结" → "明确排除"组织。

## 一、1.0 的先决条件(全部完成才发 1.0)

### API 面审计

- [ ] **错误信封 v1 冻结**:`{"code","msg","data","page"}` 字段名与类型;
      框架错误码 = HTTP 状态码、`code == 0` 即成功的约定写入文档并承诺不变
- [ ] **`Resp<T>` 构造器面收敛**:确定 `ok/created/page/err/err_msg/with_status`
      为稳定集;`page` 字段命名(index/size/total)冻结
- [ ] **Context 提取方法签名审计**:全部 `&self` + 内部可变性的约定、
      `body_stream` 与缓冲提取的互斥语义、错误类型与消息格式(格式是
      可变细节,但"层+字段+类型"结构承诺不变)
- [ ] **Handler/Middleware trait 形状冻结**:`fn call(&self)` + Clone 约束 +
      `Arc<dyn Fn>` 擦除是实现细节,但"普通 async fn 直接注册"的用户
      契约冻结
- [ ] **semver 策略文档化**:1.0 起破坏性变更走 2.0;feature 门控的
      增加(tls/ws/gzip/openapi/…)视为非破坏
- [ ] **MSRV 策略**:跟随 Rust stable - 2;edition 随工具链但 MSRV 提升只走 minor

### 缺口补齐(小而值得)

- [ ] `Response` 的 `Set-Cookie` 直接 helper(中间件后置场景)
- [ ] `ServeDir` 目录列表(可选 `.files_listing()`,纯 HTML,无依赖)
- [ ] SSE `keep_alive()` 帮助(定时 comment 帧,防代理空闲断连)
- [ ] WebSocket `Message` 的便利封装评估(是否暴露 tungstenite 原生类型 ——
      倾向继续原生,文档写明)
- [ ] 错误响应的 `Retry-After` 等常用头 helper(按需,YAGNI 优先)

### 质量门槛

- [ ] 测试覆盖公开面全部行为分支(当前 60+,1.0 前做一轮 gap 审计)
- [ ] docs.rs 零警告 + 每个公开类型至少一个可用示例
- [ ] 基准说明页:与 axum 的同机吞吐对比发布为"参考数据"而非卖点
- [ ] 安全:依赖 `cargo audit` 进 CI;静态文件/信封路径 fuzz 一轮

## 二、有意冻结的决策(1.0 文档明示"不是 bug")

1. **owned Context**:`async fn(ctx: Context)` 不改;借用式 + proc-macro 的
   路线已论证并放弃(见 specs/2026-09-17 设计文档 §4)
2. **统一信封默认全局**:非信封出口只有 `Json<T>` / `Html<T>` / 手工 Response;
   不提供"按路由关闭信封"的开关
3. **不兼容 Tower**:中间件生态自建;兼容层不在 1.0 承诺内(用户要求可作
   独立 crate `desire-tower` 评估,但不是核心)
4. **业务错误 HTTP 200**:信封 `code != 0` 默认 200,`with_status` 显式覆盖
5. **缓冲式 body 优先**:默认上限 2 MiB;流式走 `body_stream()`,不做
   自动 fallback

## 三、明确排除(写进文档,避免 perpetual beta)

- HTTP/3 / QUIC
- 内置 ORM / 模板引擎 / 静态资源打包
- 多 crate workspace(单 crate 是卖点,除非 proc-macro 出现)
- 异步运行时抽象(只支持 tokio —— hyper-util 事实标准)
